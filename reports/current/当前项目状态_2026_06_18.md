## 2. 预测模块当前状态

### 2.1 当前预测目标

当前预测模块仍然是 SKU-date 粒度：

```text
样本粒度：sku_id + date
预测窗口：未来 30 天
输出 1：未来 30 天补货量点预测
输出 2：未来 30 天是否发生正向补货的概率
模型形式：两阶段 hurdle model
```

这里要注意：

```text
补货概率不是“预测 15 件的置信度”，而是未来 30 天是否发生正向补货的概率。
预测量是点预测，不是完整概率分布。
```

### 2.2 模型演进过程

项目模型大致经历了三步：

| 阶段 | 粒度/模型 | 解决的问题 | 主要问题 |
| --- | --- | --- | --- |
| 聚合前双塔 LSTM | `buyer_id + sku_id + date` | 保留买手和 SKU 两侧信息 | 买手-SKU 组合太稀疏，很多样本真实值为 0 |
| 聚合后 SKU-date LSTM | `sku_id + date` | 目标粒度更符合全国 SKU 补货预测 | 对大货、冷启动和稀疏事件仍偏弱 |
| 当前树模型主线 | SKU-date + 结构化特征 | 更稳定地利用静态、动态、买手、库存、事件特征 | 仍依赖生命周期、活动、库存等业务字段补齐 |

对外可以说：

> 早期双塔 LSTM 的价值是帮助我们确认买手和 SKU 两侧信息的重要性，但买手-SKU 粒度过细导致样本极度稀疏。后续我们把目标聚合到 SKU-date 粒度，并将买手行为转成聚合特征，再结合树模型增强稳定性。目前主线可以理解为保留了双塔思想中的“商品侧和行为侧信息”，但工程上主要用结构化特征和树模型来承接。

### 2.3 买手数据是否还在用

SKU 聚合后，不再预测某个买手会买多少，但买手信息没有丢，而是转成 SKU 级聚合特征。

典型特征包括：

```text
过去90天补货买手数
过去90天期货买手数
补货Top1买手占比
补货Top3买手占比
补货买手集中度
期货Top1买手占比
期货Top3买手占比
期货买手集中度
```

含义：

```text
模型不再判断“某个买手会不会买”，而是判断这个 SKU 的需求是由多个买手共同贡献，还是高度依赖少数核心买手。
```

## 4. 盈亏分析模块当前状态

### 4.1 模块定位

盈亏分析模块不是重新预测销量，而是把预测模型输出转成经营决策。

```text
预测模块：未来 30/45 天可能有多少需求？
盈亏模块：考虑库存、成本、售价、批量和风险后，是否值得补，补多少？
```

必须强调：

```text
预测量 != 推荐生产量
```

### 4.2 V1 已完成能力

当前盈亏分析模块目录：

```text
modules/profit_analysis/
```

已完成能力：

- SKU 级预测输入标准化；
- 库存、在途、生产批量、生命周期窗口输入；
- 成本、售价、残值、持有成本、缺货成本等经济参数输入；
- 历史概率校准和 45 天需求场景校准；
- SKU 输出聚合到 SKC/style 级；
- SKC 候选生产量生成；
- 多需求场景下逐日库存流和利润模拟；
- 保守、均衡、激进三种策略；
- SKC 推荐量分配回 SKU；
- 输入质量门禁、运行 manifest、推荐明细和质量报告；
- 31 项单元测试通过。

### 4.3 真实回测结果

真实回测口径：

```text
锚点：2026-02-15、2026-02-24
窗口：45天
决策粒度：style_id，即 SKC
生产约束：每个 SKC 最少 100 件，10 件递增
完整 SKC-anchor：2,682
SKU-anchor：7,853
真实未来45天需求：15,406
锚点库存：169,376
```

核心对比：

| 策略 | 正计划数 | 总生产量 | 有利计划 | 有害计划 | 相对不补货实验利润 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 不补货 | 0 | 0 | 0 | 0 | 0 |
| 直接按预测缺口 | 210 | 21,000 | 6 | 204 | -3,914,626.24 |
| 盈亏模块 | 3 | 300 | 3 | 0 | +130,980.00 |
| 事后真实缺口 | 97 | 9,700 | 15 | 82 | -769,284.18 |

解释口径：

> 这个结果不是说预测模型真实亏损 391 万，而是历史反事实回测。它说明如果直接把预测缺口机械转成生产计划，最小生产批量会放大过补风险。盈亏模块的价值是把预测信号做经济过滤，只保留少量高确定性计划。

### 4.4 盈亏模块目前边界

当前仍然是 V1 原型和决策辅助，不是正式财务系统。

原因：

- 实际成交价缺失，利润金额是代理利润/同口径策略比较；
- 每个 SKC 的真实生产周期还未完整接入；
- 已下生产单、在途、预计入仓日期不完整；
- 成本覆盖不是 100%，缺失部分仍用 `吊牌价 / 7`；
- 还没有人工采纳、修正、最终结果反馈闭环。

## 5. 商品识别量化与多模态接入

### 5.1 总体判断

甲方提出的“把感性设计洗成量化特征，形成商品基因库”方向有价值，但第一阶段不应直接承诺“用图片精准预测销量”。

更合理的落点是：

```text
图片/设计语言
  -> 商品量化标签
  -> 相似款检索
  -> 冷启动先验
  -> 生命周期曲线分组
  -> 商品企划复盘
  -> 买手偏好和防撞款辅助
```

第一阶段建议：

```text
多模态大模型 API 初标
  -> 人工复核关键标签
  -> 商品基因表入库
  -> 相似款生命周期曲线
  -> 冷启动 shadow 验证
```

### 5.2 260 个 SKU 的定位

甲方提到的 260 个 SKU 适合做第一版验证，但不够支撑模型增益验证。

260 个 SKU 适合：

- 验证多模态 API 能否稳定打标签；
- 验证标签字典是否符合甲方设计语言；
- 验证人工复核流程；
- 形成商品基因表 demo；
- 做少量相似款展示。

如果要真正接入预测模型，需要扩展到商品表中的历史 SKU/style：

```text
历史商品图片
  -> 批量打标
  -> 和历史订单/补货/库存/生命周期结果 join
  -> 验证某类设计特征是否对应稳定需求曲线
  -> 再判断是否接入预测模型
```

会议上可以这样说：

> 260 个 SKU 更适合作为第一批商品识别量化样本，用来验证标签体系和多模态 API 流程。如果后续要真正接入补货预测模型，不能只依赖 260 个 SKU，而需要把商品表中历史 SKU/style 尽量批量打标，并和历史订单、补货、库存、生命周期结果对齐。只有这样模型才能学习某类设计特征对应什么样的需求曲线。

### 5.3 成本判断

260 个 SKU 规模下，API 调用不是主要成本。

| 方案 | 内容 | 粗估成本 |
| --- | --- | ---: |
| Demo | API 打标 + 抽检 + CSV/Excel | 1,000-8,000 RMB |
| V1 | API + 人工复核 + 入库 + 审计 | 1万-5万 RMB |
| V2 | V1 + 相似款检索 + 预测 shadow 实验 | 3万-8万 RMB |
| 训练视觉模型 | 人工标签 + 微调/训练 + 评估 | 5万-20万 RMB 起步 |

判断：

```text
API 本身通常是几十到几百元人民币级别。
主要成本是人工复核、标签字典、工程接入、数据安全和预测实验。
当前不建议训练视觉销量模型，因为 260 个 SKU 样本太少。
```

### 5.4 适合优先做的场景

| 场景 | 短期可行性 | 对当前项目价值 | 判断 |
| --- | --- | --- | --- |
| 补货预测/衰退周期 | 高 | 高 | 最值得先接入，尤其帮助新品冷启动 |
| 买手级推盘 | 中 | 中高 | 需要买手销售/售罄数据，否则只能做偏好相似 |
| 商品企划复盘 | 高 | 高 | 适合先做分析报表，不一定需要复杂模型 |
| 退货归因 | 低到中 | 中 | 需要完整退货原因、退货数量和退款金额 |
| 企划防撞车 | 中高 | 中 | 可做相似度矩阵演示，对预测主线不是第一优先级 |

## 6. 特殊节点字段与误差优化

### 6.1 当前问题

甲方反馈：

```text
个别误差大的商品存在直播爆款、节日等特殊节点因素。
```

当前模型已有 Event 行为数据，可以间接捕捉点击、浏览、加购等热度变化，但还没有完整的业务节点日历。

因此当前能力边界是：

```text
能感知已经体现在行为数据里的热度变化；
不能提前知道未来计划直播、节日、订货会、主推活动。
```

1. 保留 Phase7 作为 fallback；
2. 将 `legacy_combo_listing_eligible` 作为 Phase8 formal 候选主线；
3. 6 月完整标签到齐后，做 post-freeze monitoring；
4. 基于 6.16 服务器快照重建 silver/gold，重新跑完整评估；
5. 固定数据快照、训练配置、特征版本和输出目录；
6. 输出 Phase8 模型卡和对外指标说明。

成功标准：

```text
多锚点整体优于 Phase7；
大货少补不恶化；
true=0 误报受控；
2026 新锚点收益稳定；
工程上能一键复现。
```

### 8.2 第二阶段：提高预测准确率

目标：

```text
继续降低 WMAPE，提高 4-25 和 >25 大货预测，降低 long-zero 误报。
```

重点优化：

1. 生命周期字段增强  
   使用 B2B 开售/开订、下架、停止补货、商品状态，构造生命周期相对天数、新品期、稳定期、尾货期。

2. 库存快照增强  
   使用真实有库存、真实零库存、连续零库存天数、库存覆盖天数，区分“没需求”和“库存约束导致没订单”。

3. 特殊节点增强  
   加入直播、节日、订货会、主推等 event calendar，解决突发爆款和活动后误补。

4. 商品基因特征  
   先用 260 SKU 验证标签体系，再扩展历史商品表，做冷启动相似款先验。

5. 分位数预测  
   在点预测外增加 P10/P50/P90，表达不确定性，而不是直接输出每个整数数量的概率。

### 8.3 第三阶段：提高数据可用性和展示可理解性

目标：

```text
让业务方看到的不是滚动30天抽象预测，而是可执行、可对账的固定目标预测。
```

建议做：

1. 周频正式补货 + 日频监控  
   每周形成正式补货建议；每天只监控异常变化，避免重复补货。

2. 固定终点展示  
   将滚动 30 天预测转成：
   ```text
   本周结束前预计补多少
   月底前预计补多少
   生命周期结束前预计补多少
   活动结束前预计补多少
   ```

3. 净需求计算  
   结合库存、在途、已下生产单，输出：
   ```text
   预测需求
   当前可用库存
   在途量
   已确认生产量
   净缺口
   建议补货量
   ```

4. 解释字段  
   输出为什么预测为正、为什么建议补货、是否受库存/生命周期/活动影响。

5. 人工反馈闭环  
   记录：
   ```text
   预测日期
   目标日期
   模型预测值
   模型建议量
   人工最终量
   修正原因
   最终实际订货/销售
   ```

### 8.4 第四阶段：盈亏模块 V1 到 V2

目标：

```text
从“可运行原型”升级为“可业务试用的补货决策辅助模块”。
```

工作：

1. 接入真实成本和成交价/结算价；
2. 接入生产周期、MOQ、递增粒度、产能约束；
3. 接入已下生产单、在途、预计入仓日期；
4. 加入生命周期剩余窗口，判断是否还来得及补；
5. 加入人工采纳/拒绝和修正原因；
6. 输出标准 Excel/CSV 和质量报告；
7. 做更多历史锚点回测，比较不同策略收益风险。

成功标准：

```text
不追求推荐很多单；
优先保证推荐单高确定性、低过补风险、可解释。
```

### 8.5 第五阶段：商品识别量化 V0 到 V2

目标：

```text
验证商品设计标签是否能提升冷启动、相似款生命周期和企划复盘。
```

路线：

1. V0：260 SKU API 打标试跑  
   输出商品基因表草稿、低置信度标签清单、人工抽检结果。

2. V1：人工复核和入库  
   稳定标签字典，建立 `sku_id/style_id -> 标签` 映射。

3. V2：历史商品批量打标和 shadow 实验  
   对商品表中有图片、有订单结果的历史 SKU/style 批量打标，并和补货、库存、生命周期结果对齐，验证是否提升冷启动指标。

不建议现在做：

```text
不要直接用 260 个 SKU 训练视觉销量模型。
不要承诺图片可以单独精准预测销量。
```

## 9. 会上建议争取的确认

建议最后明确问甲方：

1. `LISTING_DATE` 是否等于 B2B 实际开售/开订日期？
2. 是否能提供 B2B 实际开售/开订日期？
3. 是否能提供计划下架、实际下架、停止补货、商品状态？
4. 是否能持续提供库存快照、求购信息、Event 行为数据？
5. 是否能提供生产周期、MOQ、已下生产单、在途和预计入仓？
6. 是否能提供真实成本、实际成交价或统一结算折扣？
7. 是否能提供直播、节日、订货会、主推等特殊节点日历？
8. 商品图片是否允许使用外部多模态 API？
9. 是否能提供历史老款图片和设计/企划复核人员？
10. 商品识别量化第一阶段是优先服务冷启动预测，还是企划复盘/防撞款演示？

## 10. 不建议会上承诺的内容

- 不建议说 Phase8 已经基于 6.16 最新快照重训完成；
- 不建议说 Phase8 已完全替代 Phase7，应说候选主线，保留 fallback；
- 不建议把盈亏回测金额说成正式财务利润；
- 不建议说盈亏模块可以自动下单；
- 不建议把正向补货概率说成预测数量的置信度；
- 不建议承诺 260 个 SKU 图片能训练稳定视觉销量模型；
- 不建议承诺现在已经能提前识别直播爆款，除非甲方提供活动计划字段；
- 不建议承诺每日滚动 30 天预测可以直接等同于“到某固定日期前还要补多少”，这需要展示层或固定终点模型转换。

## 11. 最后总结口径

可以这样收尾：

> 当前项目已经从单一补货预测，推进为“预测模型 + 盈亏决策 + 数据可用性增强 + 商品识别量化调研”的组合方案。预测模块在 Phase8 中通过上市日期、库存、Event、求购等信号取得了相对 Phase7 的稳定改善；盈亏分析模块已经形成 V1 原型，能把预测需求转成更保守、更可解释的生产建议；商品识别量化方向建议先做商品基因表和相似款冷启动验证，不建议直接训练视觉销量模型。下一步最关键的是甲方补齐 B2B 实际开售/开订、生命周期终点、生产约束、真实成本价格、特殊节点日历和商品图片/标签数据。
