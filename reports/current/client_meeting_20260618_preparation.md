## 2. 盈亏分析模块设计与实现

### 2.1 模块定位

盈亏分析模块不是重新预测销量，而是接在预测模块后面做经营决策。

```text
预测模块：未来 30/45 天可能有多少需求？
盈亏模块：考虑库存、成本、售价、批量和风险后，这个需求是否值得转成生产计划？
```

所以：

```text
预测量 != 推荐生产量
```

### 2.2 当前已经完成

当前盈亏分析模块已形成 V1 原型，目录为：

`modules/profit_analysis/`

已完成能力：

- SKU 级预测输入标准化；
- 库存、在途、生产批量、生命周期窗口输入；
- 成本、售价、残值、持有成本、缺货成本等经济参数输入；
- 历史概率校准和 45 天需求场景校准；
- SKU 级输出聚合到 SKC/style 级；
- SKC 级候选生产量生成；
- 多需求场景下逐日库存流和利润模拟；
- 保守、均衡、激进三种策略；
- SKC 推荐量分配回 SKU；
- 输入质量门禁、运行 manifest、推荐明细和质量报告；
- 单元测试 31 项通过。

### 2.3 输入输出

生产式入口需要三张标准表：

| 输入 | 关键字段 |
| --- | --- |
| prediction | `sku_id`, `style_id`, `snapshot_date`, `pred_prob_positive`, `pred_qty_30d` |
| inventory | `current_inventory`, `inbound_within_30d`, `lead_time_days`, `min_batch_qty`, `increment_batch_qty` |
| economics | `unit_cost`, `unit_price`, `holding_cost`, `salvage_value`, `target_sell_through_rate`, `lifecycle_days` |

输出：

| 输出 | 含义 |
| --- | --- |
| `skc_recommendations_*.csv` | SKC 级推荐生产量和核心经济指标 |
| `sku_allocations_*.csv` | SKC 推荐总量分配到 SKU |
| `recommendation_details_*.json` | 候选生产量、需求场景、评分明细 |
| `quality_report_*.json` | 输入覆盖、成本兜底、重复键、分配守恒 |
| `run_manifest_*.json` | 运行参数和产物路径 |

最小示例中有两个 SKC：

| --- | --- | ---: |
| AK1001 | AK1001-36 | 87 |

要讲清楚：

> AK1002 并不是没有预测需求，而是库存已经足够、概率低、最小生产批量 100 件会造成过补，因此盈亏模块建议不生产。

### 2.5 真实回测结果

真实回测口径：

- 锚点：`2026-02-15`、`2026-02-24`；
- 分析窗口：45 天；
- 决策粒度：`style_id`，即 SKC；
- 生产约束：每个 SKC 最少 100 件，10 件递增；
- 完整 SKC-anchor：2,682；
- SKU-anchor：7,853；
- 真实未来 45 天需求：15,406；
- 锚点库存：169,376。

核心对比：

| 策略 | 正计划数 | 总生产量 | 有利计划 | 有害计划 | 相对不补货实验利润 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 不补货 | 0 | 0 | 0 | 0 | 0 |
| 直接按预测缺口 | 210 | 21,000 | 6 | 204 | -3,914,626.24 |
| 盈亏模块 | 3 | 300 | 3 | 0 | +130,980.00 |
| 事后真实缺口 | 97 | 9,700 | 15 | 82 | -769,284.18 |

解释口径：

> 这个结果不是说预测模型真实造成亏损，而是历史反事实回测：如果直接把预测缺口机械转成生产计划，会受到最小批量约束放大，产生严重过补。盈亏模块的价值是把预测信号做经济过滤，只保留少量高确定性计划。

### 2.6 当前边界和后续数据

当前不能说是正式财务系统，原因：

- 实际成交价缺失，利润金额是代理利润/同口径策略比较；

- 已下生产单、在途、预计入仓日期不完整；
- 成本覆盖不是 100%，缺失部分仍用 `吊牌价 / 7`；
- 还没有人工采纳/修正/最终结果反馈闭环。

## 3. 商品识别量化 / 商品基因库调研

### 3.1 对甲方想法的总体判断

甲方提出的“把感性设计洗成量化特征，形成商品基因库”方向是有价值的，但不应直接承诺“用图片精准预测销量”。

更合理的落点是：

```text
图片/设计语言
  -> 商品量化标签
  -> 相似款检索
  -> 冷启动先验
  -> 生命周期曲线分组
  -> 商品企划复盘
  -> 买手偏好和防撞款辅助
```

更具体地说，第一阶段建议采用：

```text
多模态大模型 API 初标
  -> 人工复核关键标签
  -> 商品基因表入库
  -> 相似款生命周期曲线
  -> 冷启动 shadow 验证
```

不建议当前直接训练视觉销量模型。原因是 260 个 SKU 样本太少，足够验证标签体系和 API 流程，但不足以训练稳定模型。

### 3.2 五个场景可行性判断

| 场景 | 短期可行性 | 对当前项目价值 | 判断 |
| --- | --- | --- | --- |
| 补货预测/衰退周期 | 高 | 高 | 最值得先接入，尤其帮助新品冷启动和生命周期曲线 |
| 买手级智能推盘 | 中 | 中高 | 需要买手订货和终端售罄/销售表现，否则只能做偏好相似 |
| 商品企划复盘 | 高 | 高 | 很适合先做 BI/分析报表，不一定需要复杂模型 |
| 退货归因 | 低到中 | 中 | 需要完整退货原因、退货数量、退款金额，现在不应优先承诺 |
| 企划防撞车 | 中高 | 中 | 可做相似度矩阵演示，对预测主线不是第一优先级 |

### 3.3 多模态 API 与训练路线判断

| 路线 | 数据要求 | 当前可行性 | 判断 |
| --- | --- | --- | --- |
| 多模态 API 零样本打标 | 商品图片 + 固定 schema | 高 | 最适合 V0，先跑通 260 个 SKU |
| API + 人工复核 | 图片 + 少量人工审核 | 高 | 最推荐 V1，能保证标签体系稳定 |
| 图片 embedding 相似款检索 | 图片 + 历史商品库 | 中高 | 适合做冷启动相似款和防撞款 |
| 微调标签分类器 | 几千个带标签商品 | 低 | 当前样本不够，后续再做 |
| 端到端图片预测销量 | 大量图片 + 销售/补货标签 | 低 | 当前不建议承诺 |

API 路线示例：

```text
输入：商品主图、细节图、模特图、品类、季节、价格
输出：颜色、饱和度、廓形、版型、面料、结构、设计复杂度、风格关键词、场景、置信度
```

需要固定 JSON 输出格式，例如：

```json
{
  "style_id": "xxx",
  "sku_id": "xxx",
  "color_family": "black",
  "saturation_level": "low",
  "silhouette": "wide_leg",
  "fit_level": "loose",
  "fabric_handfeel": "drapey",
  "structure_type": ["curved_panel", "asymmetric_cut"],
  "design_complexity": "medium",
  "style_keywords": ["minimal", "relaxed"],
  "occasion": ["commute", "daily"],
  "confidence": 0.82,
  "needs_human_review": true
}
```

训练路线的前提：

```text
至少几千个历史商品
每个商品有稳定图片
有人工复核标签
有销售/补货/售罄/退货结果
有明确训练目标
```

所以当前建议：

```text
260个SKU用于验证标签体系和API流程；
不要用于从零训练模型。
```

详细技术调研见：

`reports/current/client_meeting_20260618_product_gene_multimodal_research.md`

### 3.4 最建议先做的不是五个应用，而是一张商品基因表

建议先让甲方把 260 个 SKU 的设计识别结果整理成结构化表：

```text

category
season
color_family
saturation_level
silhouette
fit_level
fabric_handfeel
fabric_weight
structure_type
design_complexity
style_keywords
occasion

```

其中：

- `tag_source` 说明标签来自人工、视觉模型还是人工复核；
- `tag_confidence` 表示标签可信度；
- `visual_embedding_id` 可选，用于后续图片相似度检索。

### 3.5 对预测模块的接入方式

短期不要直接训练复杂视觉模型。建议三种低风险接入：

1. 静态商品特征  
   把设计标签作为 SKU/style 静态特征，和类目、价格、季节、上市日期一起输入。

2. 相似款生命周期先验  
   新品没有历史订单时，按设计标签找历史相似款，计算：
   ```text
   上市后第1-2周需求
   第3-5周起量概率
   第6-12周长尾程度
   是否容易断崖下跌
   ```

3. 风险分组  
   给盈亏模块提供标签级风险，例如：
   ```text
   重设计款 -> 需求波动更大
   基础款 -> 生命周期更平稳
   高饱和色 + 修身 + 挺括 -> 可能更高退货/滞销风险，需要数据验证
   ```

### 3.6 对甲方的建议口径

> 商品识别量化方向非常有价值，但第一阶段不建议直接做复杂模型，而是先用多模态大模型 API 结合人工复核形成商品基因表，并把它接入补货预测的冷启动和相似款生命周期曲线。这样既能服务当前预测模型，也能为后续买手推盘、企划复盘和防撞款分析打基础。等历史商品和人工复核标签积累到足够规模后，再考虑训练或微调专用视觉模型。

需要甲方配合：

```text

sku_id/style_id与图片的映射
设计标签定义表
人工复核标签
历史相似款标签
标签与销售/补货/库存/利润的对齐数据
标签来源、置信度、复核状态
```

## 4. 特殊节点字段与误差大的商品优化

### 4.1 4.30 反馈问题

甲方原问题：

> 对 CSV 表格中误差大的商品进行了分析，个别商品存在特殊节点的问题，例如直播爆款、节日等因素，现在对特殊节点有相关字段去辅助判断吗？

当前回答要分两层：

1. 现在有 Event 用户行为数据，但它是点击、浏览、加购等行为流水，不等价于“直播/节日/营销活动日历”。
2. 当前还没有完整的特殊节点字段，无法明确告诉模型某个 SKU 在某天会受到直播、节日、订货会、主推活动影响。

建议对外说：

> 当前模型已经接入 Event 行为信号，可以间接捕捉部分热度变化，但还没有直播、节日、活动、主推等业务节点字段。因此对突发爆款和节日拉动，只能通过事前行为变化间接感知，不能在活动发生前主动判断。

### 4.2 为什么特殊节点重要

特殊节点会造成三类误差：

1. 直播/主推导致短期突然爆发  
   如果模型没有活动字段，锚点前历史需求可能很低，模型会低估。

2. 节日/订货会导致集中订货  
   某些 SKU 或类目在特定日期前后需求集中释放，普通滚动历史均值无法解释。

3. 活动结束后需求快速回落  
   如果只看到活动期订单爆发，模型可能把短期活动误认为长期需求，造成后续误补。

### 4.3 建议新增特殊节点日历

建议甲方提供一张特殊节点表：

```text
event_id
event_name
event_type
event_start_date
event_end_date
scope_type
scope_style_id
scope_sku_id
scope_category
scope_buyer_id
scope_channel
event_strength
planned_exposure
planned_discount
host_or_live_room
campaign_owner
expected_lift
actual_exposure
actual_order_qty
```

字段解释：

| 字段 | 含义 |
| --- | --- |
| `event_type` | 直播、节日、订货会、主推、陈列、达人、折扣、上新波段 |
| `scope_*` | 说明活动影响哪些商品、类目、买手或渠道 |
| `event_strength` | 活动强度，可以先人工分 1/2/3 |
| `planned_exposure` | 预计曝光量，可选 |
| `expected_lift` | 预期拉动，可选 |
| `actual_order_qty` | 活动后真实带动量，只能用于复盘，不能作为预测时特征 |

### 4.4 特殊节点特征怎么进模型

预测时可用的特征：

```text
days_to_event
days_since_event
is_in_event_window
is_pre_event_window_7d
is_post_event_window_7d
event_type_live_flag
event_type_holiday_flag
event_type_key_style_flag
event_strength
event_scope_match
event_count_next_30d
event_count_past_30d
```

注意区分：

- 预测日前已经计划好的活动，可以作为预测特征；
- 活动后才知道的真实曝光、真实带动订单，只能作为复盘标签，不能作为预测特征。

### 4.5 未来优化路径

短期：

- 建特殊节点日历；
- 对误差大的 SKU 做 event tag 对齐；
- 在预测解释里增加“是否受活动节点影响”。

中期：

- 在 Phase9 中加入事件窗口特征；
- 对直播/节日做单独 uplift 校准；
- 区分活动爆发和自然需求，避免活动后误补。

长期：

- 做活动效果复盘：
  ```text
  活动前预测量
  活动计划强度
  活动后真实订货量
  活动后回落速度
  ```
- 形成特殊节点先验，帮助下一次类似活动提前预测。

### 4.6 这部分建议会议上怎么说

可以这样回答甲方：

> 目前我们有 Event 行为数据，可以捕捉一部分热度变化，但还没有直播、节日、订货会、主推等特殊业务节点字段。因此模型对已经在行为数据里体现出来的热度有一定感知，但对未来计划活动无法提前知道。后续建议补一张特殊节点日历，记录活动类型、开始结束日期、影响商品范围和活动强度。这样模型可以在活动前识别可能爆发的商品，在活动后识别需求是否只是短期拉动，避免把直播爆款误当成长期补货需求。

## 5. 会议中建议向甲方确认的问题

### 5.1 预测模块

1. `LISTING_DATE` 是否等于 B2B 渠道真实可订货日期？
2. 是否能提供 `b2b_launch_date` 或 `order_open_date`？
3. 是否有计划下架、实际下架、停止补货、清仓状态字段？
4. 是否能持续提供求购/意向数据增量？
5. 库存快照是否以后能按日稳定提供？

### 5.2 盈亏模块

1. 每个 SKC 的生产周期表什么时候能提供？
2. MOQ=100、增量=10 是否对所有 SKC 都长期成立？
3. 是否有已下生产单、在途生产、预计入仓日期？
4. 成本表覆盖不到的 SKC 是否继续使用 `吊牌价 / 7`？
5. 能否提供实际成交价或统一结算折扣？

### 5.3 商品识别量化

1. 260 个 SKU 是否能提供稳定的 `sku_id/style_id -> 图片/标签` 映射？
2. 标签是人工标注、模型识别，还是人工复核？
3. 标签体系是否稳定，例如颜色、版型、面料、结构、风格、场景？
4. 是否有历史老款也能补同样标签，用于相似款生命周期曲线？
5. 是否希望先做补货冷启动，还是先做企划复盘/防撞款演示？

### 5.4 特殊节点

1. 是否有直播、节日、订货会、主推、陈列、达人合作等活动日历？
2. 活动是否能关联到具体 `style_id` / `sku_id` / 类目？
3. 活动强度是否能分级？
4. 是否能提供活动计划日期，而不仅是活动后结果？
5. 是否能提供活动后的真实曝光或带动订单，用于复盘？

## 6. 建议结尾

建议收尾口径：

> 预测模块已经从 Phase7 推进到 Phase8，核心进展是上市日期、库存、Event、求购等业务信号接入后，多锚点评估整体优于 Phase7。盈亏分析模块已经形成 V1 原型，可以把预测需求转成 SKC 级生产建议。下一步如果甲方能补充 B2B 实际开售/开订、生命周期终点、生产周期、真实成交价/成本、特殊节点日历和商品设计标签，我们就能从“预测补货量”继续推进到“解释为什么补、什么时候补、补多少最划算”。

## 7. 会上不建议承诺的内容

- 不建议承诺仅凭 260 个 SKU 图片就能准确预测销量；
- 不建议把当前盈亏金额说成审计财务利润；
- 不建议说直播/节日已经被模型完整识别；
- 不建议说 Phase8 已经基于 6.16 最新快照重训；
- 不建议把滚动 30 天预测直接解释成固定日期前剩余需求。
